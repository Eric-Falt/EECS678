Ch1: OS Goals, Operation, Evolution

OS = intermediary between user & hardware.

  • User view: ease of use, abstraction, powerful instructions, easy to run programs.
  • System view: resource allocator (CPU, memory, I/O, files, network); control program.

OS goals: execute user programs; make solving easier; convenient; efficient hardware use.

Components: Hardware → OS → Application programs → Users.

Boot / Operation

  • Bootstrap initializes CPU regs, device controllers, memory; loads OS kernel.
  • OS is interrupt-driven.
  • Interrupt → CPU transfers to ISR via Interrupt Vector Table (IVT) (fixed address).
  • Dual-mode: user mode & kernel mode. Privileged instructions only in kernel. Syscalls/interrupts/returns change mode.

  • Address space separation.
  • Dual-mode + privileged instructions.

  • System calls controlled entry to kernel.

Ch2: OS Services, Syscalls, Structures, VMs

User services: UI (CLI/GUI/touch), program execution, I/O, file-system manipulation, IPC, error detection.

Efficient operation: resource allocation, accounting, protection & security.

System Calls

  • Programming interface to OS services; request privileged service.
  • Usually via API (Win32, POSIX) rather than direct syscall.
  • Implementation: software trap; register holds syscall number.
  • Parameter passing: registers (fast, limited); block/table on stack (pass stack location in reg); stack (push/pop).

Syscall Types & Examples

  • Process control: fork(), exit(), wait()
  • File management: open(), read(), write(), close()
  • Device management: ioctl(), read(), write()
  • Information maintenance: getpid(), sleep(), alarm()
  • Communications: pipe(), shmget(), mmap()
  • Protection: chmod(), umask(), chown()

System Programs

File mgmt (mkdir, cp, rm, ls); status (date, ps, top); modify (vi, grep, find); lang support (gcc, gdb); load/exec; comm (ssh, mail, ftp).

Toolchain

Source → Compiler → Assembly → Assembler → Object → Linker → Executable → Loader → Program in memory.

Design

Policy = what; Mechanism = how. High-level lang: easier, portable; assembly: efficient.

Virtual Machines

  • Hypervisor controls host hardware; guest gets virtual copy.
  • Benefits: multiple OS, isolation, testing, consolidation.
  • Java VM: class loader + Java interpreter → portability.

Ch3: Processes, Scheduling, IPC

Process vs Program

  • Program = passive (text only). Process = active (program in execution).
  • Process has: code, data, PC, heap, stack, registers, PCB.

Process Memory

RegionHoldsAllocation
TextProgram binaryOn creation
DataGlobal/staticOn creation
HeapDynamic dataExplicit/implicit
StackLocal vars, function callsAutomatic

Process States & Transitions

  • New → Ready → Running → Terminated
  • Running → Waiting (I/O/event wait)
  • Waiting → Ready (I/O/event completion)
  • Running → Ready (interrupt)
  • Ready → Running (dispatch)

PCB

State, PC, CPU regs, scheduling info, memory mgmt info, accounting, I/O status.

Context Switch: save current process state, restore next. Overhead. Mode switch ≠ context switch.

Scheduling

  • Job queue = all processes; Ready queue = ready; Device queues = waiting I/O.
  • Long-term: selects jobs into ready queue; controls degree of multiprogramming.
  • Short-term: selects next process for CPU; invoked frequently.

Process Creation / Termination

  • fork() creates child; exec() replaces memory; wait() waits.
  • Sharing: all, subset, none (Unix). Execution: concurrent (Unix) or wait.
  • exit() terminates; OS deallocates. Parent may abort child. Orphan on Unix gets new parent.

IPC Models

Shared MemoryMessage Passing
FastSlower
ConvenientEasier for distributed

Message Passing: send(), receive(). Direct (name proc) vs indirect (mailbox/port). Blocking vs non-blocking. Buffering: zero, bounded, unbounded.

Unix IPC Mechanisms

  • Pipes: anonymous, parent-child, unidirectional, FIFO, exists with processes.
  • FIFOs: named, unrelated processes, half-duplex, persists.
  • Message queues: msgget, msgsnd, msgrcv, msgctl; typed messages.
  • Shared memory: shmget, shmat, shmdt, shmctl.
  • Sockets: Unix domain. Server: socket, bind, listen, accept, recv/send, close. Client: socket, connect, send/recv, close.
  • RPC/RMI: stubs marshal parameters.

Ch4: Threads — User vs Kernel Level Only

Thread = lightweight process. Independent flow of control.

  • Shared: code, data, open files, signals, cwd, uid/gid.
  • Own: thread ID, registers, stack pointer, stack, signal mask, scheduling props, return value.

Benefits: responsiveness, resource sharing, economy, scalability.

Linux Threads

  • Called tasks.
  • Created via clone().
  • Flags: CLONE_VM (same memory), CLONE_FS (fs info), CLONE_FILES (open files), CLONE_SIGHAND (signal handlers).

High-Yield Comparisons

  • Multiprogramming vs Time-sharing: throughput vs response time.
  • Process vs Thread: separate addr space vs shared; expensive vs cheap context switch; strong vs less protection.
  • Shared Memory vs Message Passing: fast/sync vs slower/easy.
  • User vs Kernel Threads: fast/blocking/no SMP vs slower/blocking handled/SMP.
